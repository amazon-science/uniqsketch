# Changelog

All notable changes to this project will be documented in this file.

## 2.0.0 (unreleased)

### Features
* `uniqsketch`: added `--tree=T1,T2,...` to build a hierarchical (multi-resolution) index instead of a single flat sketch. References are clustered at each comma-separated unique-k-mer threshold — thresholds are sorted descending so the first is the coarsest level — producing a nested tree whose internal nodes are cluster representatives and whose leaves are individual references. The tree structure is written to `<outdir>/tree_index.tsv`, a coarse sketch per internal level to `<outdir>/sketch_level_<L>.tsv`, and the full-resolution leaf sketch to the usual `-o` output. Coarse levels summarize groups of near-identical references; fine levels resolve individual strains.
* `querysketch`: added `--tree=DIR` to query a hierarchical index. Pass the `uniqsketch --tree` output directory (containing `tree_index.tsv` and the `sketch_level_*.tsv` files) as `--tree` and the leaf sketch as `--ref`. The query narrows candidates coarse-to-fine: the coarsest level is queried first, and only references whose cluster representative clears the hit/read thresholds are carried to the next finer level, so the search focuses on promising sub-trees rather than scoring every reference at full resolution.
* `uniqsketch`: `--cluster` now uses a near-linear MinHash strategy (bottom-s sketch, inverted-index candidate generation, and representative-linkage union-find) in place of the previous all-pairs O(n^2 × genome) unique-k-mer computation, making clustering of large reference sets (thousands of genomes) practical. The new `--exact` flag restores the original exact O(n^2) clustering for small sets or when exact unique-k-mer counts are required.

* `querysketch --tree`: reports at the finest level it can resolve. When a coarse-level cluster representative clears the reporting thresholds but none of its member leaves can be told apart, the result now contains a `family` row for that group, named by its node in `tree_index.tsv`, instead of nothing. The coarse level is far more sensitive for near-identical strains — a representative competes only with distant genomes, so its signature pool is orders of magnitude larger than any member's (94,406 vs 151 candidates on the 8-genome set) — and previously that evidence was discarded. Coarse-level pruning is also now permissive (`--tree-prune=N`, default 1: keep any sub-tree with at least N hits and one read), because a sub-tree pruned at a coarse level could never be recovered, which made the tree strictly less sensitive than a flat index. Measured at the 0.01% detection floor over 56 mixtures: leaf-level detections 15 → 19 (from permissive pruning) plus 6 family-level calls, so samples with signal rose from 15/56 to 25/56. Output on resolvable samples is unchanged.
* `uniqsketch --tree` / `querysketch --tree`: within-group leaf signatures. A leaf's ordinary signatures are its k-mers that occur in no other genome of the index, and for a strain with close relatives that pool is small mostly for a reason unrelated to the relatives: what the strain does not share with its siblings it usually shares with some unrelated genome elsewhere in the index, so global uniqueness discards it. On 120 *E. coli* genomes the k-mers of a strain absent from its siblings but present somewhere else outnumbered its globally unique k-mers by a median 3.2× (26× for the strain with the smallest global pool). `uniqsketch --tree` now also selects, for every leaf, k-mers unique within its group (the leaves under its parent node) with the same margin and filters, and records each one's *carriers* — the other genomes of the index that contain it — in `<outdir>/sketch_group.tsv`. `querysketch --tree` scores a within-group signature at the leaf level only when none of its carriers is itself a candidate after the coarse levels, so a read from a carrier that is present can never be credited to the leaf; the globally unique signatures stay in use throughout, so the extra set adds evidence and never removes any. On the *E. coli* index this added 200,151 signatures over the 76 leaves that have siblings (the strain with the smallest global pool has 1,255 globally unique signatures and gained 2,083); on the 280-mixture sweep, strain-level resolution of close members at 0.01% rose from 8/28 to 11/28 with 0 false rows, and on a 36-mixture benchmark of sibling pairs at 0.01–0.1% the supporting reads for that smallest-pool strain in the three mixtures containing it at 0.1% rose from 1, 4 and 1 to 28, 51 and 53, the last of which moved from a family-level to a strain-level call; the read-origin oracle found 0 noise reads on the contaminant in all 36. Carrier masking was exercised, not idle: it withheld signatures in 117 of the 280 sweep mixtures (up to 2,180 in one), and the sweep produced 0 false rows. Both tools take `--no-group-signatures` to opt out (at build time the file is not written and `build_params.tsv` records `group_signatures 0`; at query time the file is ignored). On the 8-phage index the set is 23 signatures and the 280-mixture detection table is unchanged.
* `querysketch`: the primary output gains four appended columns — `reads` (distinct supporting reads), `sigs_hit` / `sigs_total` (how many of the reference's signatures were observed), and `resolution` (`strain` or `family`). The original three columns are unchanged, so existing parsers keep working. These expose the evidence behind each call, which the abundance figure alone hides: two references can share an abundance while one rests on thousands of reads and the other on three. `reads` is per-call evidence and is not comparable across references — a read overlapping several packed signatures counts once in `reads` but several times in `count`, and near-identical strains have their few unique k-mers concentrated in short regions, so at equal depth their `reads` can differ 20-fold from a distinct genome's while `count` agrees. This is exactly why `count`, not `reads`, remains the basis for abundance (a read-based estimator was measured at 100× worse error); `count / reads` is the per-read multiplicity and a useful flag for calls carried by a handful of reads on a signature cluster.

### Changes
* `uniqsketch --tree`: signatures are now selected with `--min-margin=2 --strict-margin` by default (pass `--min-margin=1` to opt out; flat builds are unchanged). A tree index exists to separate close relatives, and margin-1 signatures fail there in a specific way: a signature one substitution from a k-mer of an abundant sibling is hit by every read of that sibling carrying a sequencing error at that base. At ~2700× coverage and a 0.3% error rate that is a few reads per site — more than a member present at 0.01% contributes in total. Measured with a read-origin oracle (simulated read ids carry their source genome) over the 28 close-relative 0.01% mixtures of the 8-genome set: margin-1 signatures collected 60 error reads on the true low-abundance member against 31 genuine ones, and 2093 reads on members absent from the sample, giving 42 false strain calls; margin-2 strict cut the absent-member reads to 2 and kept 25 of the 31 genuine reads, with the close members retaining 62–99% of their candidate pools. On 120 complete *E. coli* genomes at k=81 every reference kept at least 244 strict-margin signatures of 1000 requested (mean 75%). The selection parameters are recorded in `<outdir>/build_params.tsv`.
* `querysketch --tree`: the read cutoff defaults to 0 when the index's `build_params.tsv` says it was built with `--min-margin=2 --strict-margin`, so calls supported by a single read are reported. On such an index a foreign read needs two coincident errors to hit a signature, so one read is real evidence, and at the detection floor it is often all there is: a member at 0.01% in 3M read pairs leaves 0–4 reads on its distinguishing loci, and requiring 3 capped strain-level detection at 4 of 28 mixtures no matter how signatures were chosen. With the new default, strain-level detection of close members at 0.01% rose from 3/28 to 16/28 (every mixture with any evidence); 7 of the remaining 12 are still reported at family level, and the other 5 have a sibling as the dominant strain, so their family is already resolved to it. The cost is 2 single-read false calls in 280 mixtures (both below 0.1% abundance, `count` 10 and 20, where genuine single-read calls carried 24–71). An explicit `--rcutoff` always wins; indexes without a strict margin or built by an earlier version keep the cutoff at 2 and say so on stderr. Flat queries are unchanged.
* `querysketch`: abundance is now computed from hits per signature (`count / sigs_total`) rather than raw `count`. Raw counts are proportional to coverage only while every reference carries the same number of signatures; a close relative whose whole candidate pool is smaller than `-c` gets fewer, and a tree index built with a large `-c` makes that the normal case. On the 8-genome set with `-c500` (119–500 signatures per reference) a 10% contaminant was reported anywhere from 2.6% to 32% by raw count and from 9.3% to 11.3% by hits per signature (mean absolute error 6.2 vs 0.18 percentage points). With equal signature counts the two definitions coincide, so existing indexes report the same abundances as before. Family rows are normalised the same way, so a family's abundance is on the same footing as a strain's.
* `comparesketch`: unified the memory controls into a single `-m, --mem=N` budget in GB for reference caching (default 64). The tool caches as many second-list references as fit within the budget and streams the remainder, so peak memory stays bounded regardless of reference-set size. `--low-mem` is now an alias for `--mem 0` (fully streaming). Similarity output is unchanged.
* `uniqsketch` / `querysketch`: harmonized Bloom-filter sizing between the flat and tree code paths. The flat paths now use the same `resolveBloomSizes` fallback as the tree paths, so low-coverage inputs that previously aborted on the flat path (but succeeded on the tree path) are handled consistently.

### Fixes
* `uniqsketch`: a gzip-compressed reference FASTA produced a wrong index without a word. The k-mer counting step read gzip, so the filters were sized correctly, but the scanners read the compressed bytes as sequence: the genome contributed no k-mers and got no candidates, every k-mer it shared with another genome became that genome's "unique" k-mer (on a two-phage test the other genome's pool grew from 143,601 to 167,460 candidates), and the build exited 0. Reference scanning now goes through one gzip-aware line reader (`GzLineReader`, `scanFasta`), so a `.gz` reference builds the same index as its plain file, byte for byte; filter sizes that were taken from the compressed file size (`loadBFfaGroup`'s seen filter, `estimateMaxGenomeSize`) use the uncompressed size; and a reference's name drops the `.gz`/`.bgz` suffix as well as the extension, so `x.fa.gz` is `x`, as `x.fa` is. Two conditions that used to pass silently are now reported: a reference that yields no k-mers of length k (empty, not FASTA, or every sequence shorter than k) and one with no unique k-mers (a duplicate of another reference) each get a warning naming the file, and two references with the same base name (`a/x.fa` and `b/x.fa`), which would have overwritten each other's candidates and been one name in every output, are an error. Indexes built from plain files are unchanged (E. coli tree, flat, phage tree and flat all byte-identical).
* Tree mode failed on any tree deeper than the 8-phage benchmark's. `buildHierarchicalTree` creates a node only at the level where a merge happens, so a node whose parent is two levels up is implicitly present in between, an orphan node is present at every coarser level, and a leaf that never merged is present, as itself, everywhere. Neither side accounted for that. The build made each level's sketch from the nodes numbered with that level (on a 120-genome *E. coli* tree the level-2 sketch came from 3 genomes, so its "signatures" were shared with most of the other 117 and every sample hit them by the hundred thousand), and the query kept a reference in play only if one of its leaves had survived the level above, so singletons and orphans were filtered out before they were ever scored. Every *E. coli* query ended with 0 candidate leaves, no strain rows and two dozen family rows for clusters absent from the sample. `treeLevelPartition` now defines, for every level, the representative of each leaf (the ancestor spanning that level, or the leaf itself), and both `uniqsketch` and `querysketch` use it; the build skips a level whose partition repeats the next finer one, and the query drops a leaf from the candidate set only when a representative covering it was scored and fell below the pruning floor. Phage index and output are unchanged.
* Coarse-level signatures are now unique against every genome in the index, not only against the other representatives. A representative's k-mer shared with a member hidden behind another representative used to count as a family signature and collected that member's reads; on the *E. coli* sweep this produced 1906 spurious family rows (a handful of a node's signatures hit by hundreds of reads, up to 0.26% abundance). `identifyGroupUniqKmers` counts each k-mer once per node, so a k-mer present in several members of one node and nowhere else is that node's signature while a k-mer present in any other node's member is a repeat. Family rows are also reported once per node (the finest level) and not for a group whose sub-group is already reported.
* Coarse-level signatures no longer include k-mers that occur more than once inside the representative. `loadBFfa` marks a k-mer solid on its second sighting, so a leaf never gets a repeated k-mer as a signature. `loadBFfaGroup` counts each k-mer once per node, which is what lets a k-mer shared by every member of a node be that node's signature, but counting once also meant the second copy inside a single genome never reached the solid filter, so the repeat stayed a family signature. Multi-copy k-mers sit in mobile elements, which makes them the sequence most likely to be present in organisms outside the index entirely, and they drew reads accordingly. On a 12-genome *E. coli* tree (`-c5000 --min-margin=1`, MS8345 as representative) 209 of the 5,000 level-0 signatures and 399 of the 10,000 level-1 signatures were repeats of their own representative, against 0 in the leaf sketch, and those repeats occurred verbatim in a genome of a different genus 16× as often as single-copy signatures did (5.6% against 0.35%, over *Citrobacter*, *Enterobacter*, *Klebsiella*, *Salmonella* and *Bacteroides*). Querying SRR061226, a human gut metagenome holding no *Escherichia* at all, produced a family call for the node on 242 reads over 5 of its 5,000 signatures; four of those five were the two inverted copies of an `erm(B)` macrolide-resistance methyltransferase, a gene gut organisms carry on mobile elements. `loadBFfaGroup` now applies `loadBFfa`'s rule to the representative — the one genome candidates are drawn from, so the only one whose internal multiplicity can reach a signature — and a k-mer occurring twice there is solid. The false call is gone (the node now reaches 0 candidate leaves), signatures per level are unchanged because selection backfills from the rest of the candidate pool, and detection is unaffected: the representative's own reads, a 0.05% spike of it into a foreign background, and reads from a close relative absent from the index all give byte-identical output. A false positive in the new filter costs a signature rather than admitting a bad one, the opposite of the seen filter's exposure. Flat and `--cluster` builds never reach this code path and are unchanged; existing `--tree` indexes need rebuilding to benefit.
* `querysketch --tree`: restored the read-level log (`logread_<out>`), which the family-reporting change had dropped from tree queries. Both writers now share the same log code. The read log also lists references supported by a single read (previously only those with two or more), matching the README's description and covering the cases that matter most at low abundance.
* Fixed a data race in `BloomFilter::insert_make_change` that made index construction non-deterministic and could turn a shared k-mer into a signature for two references at once. The individual bit writes were atomic, but the composite "was this k-mer newly inserted?" answer was not: two threads inserting the same k-mer could each win a subset of the hash bits and both report success. `uniqsketch` builds its distinct/solid filter pair in parallel and relies on exactly one caller observing success, so that a k-mer occurring in two references is recorded as a repeat and excluded from both. When the race hid the repeat, the k-mer stayed a signature for both references and reads from one inflated the abundance of the other. The test-then-insert sequence is now serialised on a lock striped by the leading hash, so inserts of the same k-mer are ordered while unrelated k-mers stay parallel; the lock is only taken when the k-mer looks absent, so cost is per distinct k-mer and index build time is unchanged. Index builds are now byte-identical across runs, and `querysketch --solid` and signature selection are likewise deterministic. Measured on an 8-genome set with near-identical members: before the fix, repeated builds differed and a spurious reference was reported at up to 15% abundance in 2-3 of every 6 builds; after it, six consecutive builds are identical and the spurious call is absent in all configurations.

### Internal
* `querysketch --tree` reads the sample once. It used to run one pass over the reads per tree level, plus one for ntCard: on the 120-genome *E. coli* index six parses and six hashings of the same 3 M reads (4 billion k-mer hashes) for one result. Every level's sketch and the within-group signatures now go into one index and the level-by-level narrowing, family calls and carrier masking are applied to the tallies afterwards; the same k-mer can be a signature at several levels and every matching entry counts, which is what the separate passes added up to. The index itself changed from a `std::unordered_map` of vectors to entries sorted by hash behind an open-addressing table with a one-hash Bloom prefilter in front, so the miss that almost every k-mer position is costs one probe into a 4 MB table that stays in cache; it does not own the signature sequences (one copy instead of four, ~170 MB less). Reads are parsed by one thread per input file into a bounded queue that the OpenMP team drains, so parsing and hashing overlap; before, the workers sat idle while the main thread parsed each batch and the tool could not get past six times its single-thread speed however many threads it had. Read names are recorded once per hit read and the per-reference sets are built at the end in parallel instead of by inserting into `std::unordered_set` from the serial merge, which cost as much as the hashing. The sample's k-mer cardinality (a full pass over the reads and a 512 MB counter table) is only estimated when `--solid` needs it to size the read filter; nothing else used it. Sketch and group-sketch files are parsed by hand rather than with an `istringstream` per line (1.8 s on this index). Measured on one 3 M-read mixture at 32 threads: *E. coli* tree query 25.5 s → 3.3 s (index load 1.3 s, read pass 1.2 s), peak memory 1.26 GB → 0.92 GB; 8-phage tree query 5.6 s → 1.0 s; 8-phage flat query 3.3 s → 0.8 s. Every output is unchanged: the result table and `log_` file are byte-identical and the `logread_` read sets identical over the 280 *E. coli* mixtures (tree and flat), the 36 sibling-pair benchmark mixtures (with and without group signatures) and the 280 phage mixtures (tree with and without group signatures, and flat). The order of read ids within a `logread_` line was never deterministic across runs and is not now.
* `uniqsketch`: candidate files are binary. Each reference's unique k-mers were written as text, one line per k-mer with the 81-base sequence spelled out and the contig header repeated: 162 bytes each, and for a 120-genome tree index 22 GB written, read back, parsed with an `istringstream` per line and sorted, at every level. A candidate is now a `uint32` position in its contig (`<outdir>/<name>.cand`: a header naming the reference FASTA, then per contig its name, length and position list), and selection recomputes the sequence for the few thousand candidates per reference it examines, from the FASTA, which it reads once. Candidates are ordered by (contig name, position) as before, so the sketches are byte-identical: leaf, every coarse level, the within-group sketch and `build_params.tsv` on the *E. coli* index, and the phage tree and both flat indexes. Scratch under `<outdir>` fell from 25 GB to 873 MB (phage: 91 MB to 4 MB), peak build memory from 8.8 GB to 5.3 GB, and the *E. coli* tree build from 169 s to 153 s at 32 threads (`checkRef`, which formatted the text, was 26 % of single-thread build time). The three hand-written FASTA loops in the build (`loadBFfa`, `checkRef`, `loadBFfaGroup`) and the fourth in the carrier search are one function, `scanFasta`, so a position recorded by one scanner means the same base to all of them. Analysis scripts that read the old text files need `readCandidates` or the reference FASTA to get sequences.
* `uniqsketch --tree`: the within-group signature build runs as flat parallel job lists rather than one group after another. Filter sizes are still measured per group (ntCard runs its own parallel region), but candidate identification is one list of (group, genome) jobs with every group's filters of a batch live at once — a batch takes as many groups as fit in the memory the main build's filters already used, so peak memory does not grow with the number of groups — and selection is one list of (group, leaf) jobs writing to per-job buffers, so the output order is fixed. Candidate files are written only for the leaves that are selected from (a node's direct leaf children), not for every member. On the 120-genome *E. coli* index the group build went from 1,119 s to 49 s at 32 threads (cardinality 9.5 s, candidates 13.6 s, selection 24.6 s, carriers 1.4 s, with the ntCard change below) and the whole tree build from 1,379 s to 306 s, 19% more than the 257 s of a build without within-group signatures; `sketch_group.tsv` is byte-identical to the sequential build's and the leaf and coarse sketches are unchanged.
* `isTwoSafe` (the `--min-margin=2` check) no longer rehashes each of a candidate's 3k Hamming-1 neighbours from scratch. ntHash is an XOR of one term per base, and the vendored header already holds every term pre-rotated (the sliding functions use them to drop the outgoing base), so substituting one base is two XORs per strand: the k-mer is hashed once and each neighbour's canonical multihash follows in O(1) (`NTMC64sub` in `nthash.hpp`). Selection cost per candidate falls from 243 hashes of 81 bases to one, plus the 243 Bloom probes as before. Verified bit-for-bit against the full rehash on 94,080 substitutions across k = 21…100, and end to end: the E. coli tree index (leaf, coarse and within-group sketches), the phage tree index and the flat strict-margin phage index are byte-identical to the previous build. The E. coli tree build (120 genomes, `-c5000`, 32 threads) went from 306 s to 169 s with within-group signatures and from 257 s to 136 s without; the within-group selection phase from 24.6 s to 8.1 s. Since margin 2 is the `--tree` default, this is the cost every tree build pays; the whole E. coli build is now 8× faster than the first within-group implementation (1,379 s).
* `getCardinality` no longer computes ntCard's full k-mer frequency spectrum. The estimator's `compEst` derived f₂…f₆₅₅₃₆ with an O(covMax²) recurrence — about 1.9 s per call — and nothing read them: the filters are sized from F₀ and f₁ alone. Those two are computed exactly as before, so every filter size, index and result is unchanged (checked against the previous code on the 120 *E. coli* genomes: distinct 65,548,934 and solid 39,218,688 in both). Each call now costs ~0.4 s, which saves 2 s per query, 4 s per index build, and 50 s in the within-group build above (27 groups).
* Replaced the mutable `namespace opt` globals (42 variables defined at file scope across the three `*Util` headers, 267 usages) with one config struct per tool — `UniqSketchConfig`, `QuerySketchConfig`, `CompareSketchConfig` — passed explicitly to every function that needs settings. The globals meant no two `*Util` headers could be included in one translation unit (each defined the same names), no function could be tested under two settings in one process, and `buildSketch` mutated the entropy ceiling as a side effect, which forced the tree path to snapshot and restore nine globals around every level. All three problems are gone: the headers compose, tests build their own configs side by side, the ceiling is a const method, and the tree path copies the config per level. Behaviour is unchanged — indexes, sketches and query outputs rebuilt with the refactored binaries are byte-identical to the previous ones. Added `headerstest`, which compiles every `*Util` header into one translation unit so the fix cannot silently regress (it produces 18 errors against the previous headers).
* Cache-line-blocked Bloom filters (`vendor/BlockedBloomFilter.hpp`, now what `BloomFilter` names). The standard filter touched one random cache line per hash function and did a 64-bit modulo for each; the index build is memory-bound on exactly that traffic, since the filters are far larger than cache and on a bacterial set 89% of k-mer sightings in `loadBFfa` are repeats, which probe all five lines and then set five more in the solid filter. The blocked filter has the leading hash pick one 512-bit block (a multiply-high, no division, exact sizing) and the other hashes pick bits inside it, so an insert or a hit is one line. A miss was already about one line on the standard filter (early exit on the first unset bit at low fill), so `checkRef` and the 243 margin probes per candidate are unchanged, and that bounds the gain: measured 1.46x on the 120-genome *E. coli* tree build (150 s to 103 s at 32 threads), 1.55-1.59x on a 12-genome set, nothing on the phage set, whose filters fit in L2. Memory is unchanged (RSS within 2%). The cost is a higher false-positive rate at equal size, 6e-7 against 5e-8 at the default 128 bits per element with five hashes, which drops a candidate rather than admitting one: on the 120-genome build 11 of 25.9 M candidates, after which selection redraws about 2% of signatures from the near-identical pools. Both 280-mixture sweeps (8 phages, 120 *E. coli*) score identically to the decimal against the standard-filter indexes: same detections, same family calls, same false rows, same abundance error. Query time is unchanged (the only query-side filter is the `--solid` read filter, whose inserts are mostly first-sighting misses). The standard filter stays available as `StandardBloomFilter`; `-DUNIQSKETCH_STANDARD_BF` makes it the default again, and `test/bfbench.cpp` benchmarks the two side by side. Indexes built with the two filters differ in which signatures were drawn, so an index should be built and queried with the same filter; the build records its layout as `bloom_filter` in `build_params.tsv` and `querysketch --tree` warns when its own differs (older records without the field stay silent). `comparesketch` at its thin `-b 16 -d 3` default sees a 1.06x higher false-positive rate, which marks ~3e-4 more of each genome's k-mers as shared: on the 120 *E. coli* genomes the unique counts shift by a median 3.7e-4 relative and the similarity column by at most 4.6e-4, and of the clustering thresholds used here only a pair sitting 0.055% from the 1,000,000 line changes side, which any thin filter would do.
* `uniqsketch`: a tree level's large groups are scanned by every thread (`loadBFfaGroupParallel`). `identifyGroupUniqKmers` ran one group per thread, so a level took no less than the serial scan of its largest group: on the 120-genome *E. coli* build the top level's filter phase was 12.2 s at 32 threads, 11.1 s of it the 20-genome cluster alone, and the 12-genome MS8345 set, whose coarse levels are single groups, did not speed up past 16 threads. A group larger than an even share of the level's genomes is now scanned by all threads, one such group at a time, before the rest go one per thread, largest first. The work is split by hash rather than by file so the result is exactly the serial one: every filter is blocked and its block count is now a multiple of 256 (`BloomFilter::PARTITIONS`, at most 16 KB extra per filter), so the k-mers whose leading hash falls in the *p*-th 1/256 of the hash space own the *p*-th 1/256 of the blocks of every filter; contigs are read in file order and hashed in parallel into per-partition buckets, then one thread per partition replays its k-mers in file order, and each block sees the serial sequence of operations from a single writer (no stripe locks: `insert_make_change_exclusive`). Splitting by file would not be equivalent, since which k-mers a Bloom filter mistakes for present depends on insertion order. On the MS8345 set the coarse levels are byte-identical between `-t1` and `-t16/32/48/96`, and the build goes from 21.3 s to 9.3 s at 32 threads (one thread unchanged at 55 s); the *E. coli* build goes from 106 s to 87 s at 32 threads (three runs each) with peak RSS 6.0 → 4.4 GB, the level-0 candidate phase from 13.2 s to 5.9 s. Rounding the block counts moves every filter's hash-to-block map, so a different handful of candidates fall to false positives and about 10 % of each level's sketch lines are redrawn from the same pools, as with the blocked filter itself; both 280-mixture sweeps and the negative control were rerun (see `docs/v2.0-validation.md`). Also: filters are zeroed in parallel instead of by one thread per level and per group; `-t` is applied before the tree is built (it used to reach the level builds only as a side effect of the cardinality estimate); each level prints its candidate and selection time; the standard filter (`-DUNIQSKETCH_STANDARD_BF`) keeps the serial scan.
* Run-to-run reproducibility of a tree build, measured (`scripts/repro_runs.sh`, three *E. coli* builds each with this code and with 94e4117): in each set one run of three differed from the other two in one reference's candidate count, by one k-mer, which selection amplified to 1117 (94e4117) or 2402 (this code) sketch lines, because the slot width `total / needed` shifts every slot boundary. The cause is a concurrent-insert false positive in a shared filter during the one-group-per-thread scans, present before this change and unchanged by it; the earlier note that a sequential and a parallel build were byte-identical described a run that happened to match. Making every level deterministic is a separate change.
* `clusterReferences` and `comparesketch` reset their per-thread filter over its whole allocation (`sizeBytes()`), not the requested bit count. The blocked filter rounds up, so the tail of the last block (up to 63 bytes since 2.0, up to 16 KB with the partition rounding) kept bits from the previous genome.
* `querysketch`: the query hot loop no longer rebuilds an 81-character string at every k-mer position. The sketch is viewed through a map keyed by the signature's canonical ntHash — the value the read iterator already computes — so a position is tested with one 64-bit probe and no allocation, with the stored sequence compared on a probe hit so a hash collision can never produce a false match. Hit tallies are accumulated per thread and merged per batch, replacing a global critical section taken on every hit and an `omp atomic` applied to a map subscript (which only covered the final increment and left the lookup unsynchronised). Results are byte-identical; the per-position cost fell 2.8× (32.3 s → 11.4 s single-threaded on a 3M-pair sample). At high thread counts the gain is smaller because the single-threaded reader is now the bottleneck.
* Added a CI workflow that builds all three tools and runs the test suite on every push and pull request, across Make and CMake with GCC and Clang. Previously the only automated check was CodeQL, so the tests never ran on a PR; the Clang legs are the first time that compiler has built the codebase.

### Validation

## 1.6.1 (2026-08-24)

### Fixes
* Fixed a data race in `BloomFilter::insert_make_change` that made index construction non-deterministic and could cause a k-mer shared by two references to be used as a signature for both. Each hash bit was written atomically, but the composite "was this k-mer newly inserted?" answer was not: two threads inserting the same k-mer could each win a subset of the bits and both report success. `uniqsketch` builds its distinct and solid Bloom filters in parallel across references and relies on exactly one caller observing success, so that a k-mer occurring in more than one reference is recorded as a repeat and excluded from every reference's unique set. When the race hid that repeat, the k-mer remained a signature for both references, and reads from one inflated the reported abundance of the other.

  The impact is limited to reference sets containing near-identical genomes, but there it is significant. On an 8-genome test set with four near-identical members, repeated index builds differed from one another and a reference that was absent from the sample was reported at up to 15% abundance in two to three of every six builds. After the fix, six consecutive builds are byte-identical and no spurious call appears in any configuration. Users who previously worked around this with `--cluster` no longer need to.

  The test-then-insert sequence is now serialised on a lock striped by the leading hash value, so inserts of the same k-mer are ordered while unrelated k-mers proceed in parallel. The lock is only taken when the k-mer appears to be absent, so its cost is per distinct k-mer rather than per occurrence and index build time is unchanged. Signature selection and `querysketch --solid` are deterministic as a result. Single-threaded behaviour is unchanged, and indexes built with earlier versions remain readable — but rebuilding is recommended if your reference set contains near-identical genomes.

### Tests
* Added a concurrency regression test for `insert_make_change`: sixteen threads released from a spin barrier insert the same k-mer, and exactly one must observe success. Verified to fail against the previous implementation and pass against the fixed one. `bloomfiltertest` now links against pthreads (`-pthread` under make, `Threads::Threads` under CMake).

## 1.6.0 (2026-08-21)

### Features
* `uniqsketch`: added `--max-homopolymer=N` to drop signature candidates containing a single-base run longer than N bp. The aggregate entropy filter scores a signature over the whole k-mer, so a short local run (e.g. a poly-G tract) is diluted and can survive; this adds a direct local-run-length gate for such indel-prone tracts. Because the filter is applied while scanning each genomic selection slot, a rejected candidate is replaced by another candidate from the same slot wherever one exists, so signature counts and spacing are largely preserved. The default (`--max-homopolymer=0`) disables the filter and leaves selection unchanged.
* `uniqsketch`: added `--strict-margin` to enforce `--min-margin` as a hard requirement. By default, `--min-margin=2` falls back to a margin-1 candidate when a selection slot contains no 2-safe option; with `--strict-margin` such slots are left empty instead, so every emitted signature satisfies the requested margin at the cost of a smaller sketch. The default (off) leaves `--min-margin` behavior unchanged.

Both options are contributed features and are off by default, so 1.6.0 is backward compatible with 1.5.0 output.

## 1.5.0 (2026-07-17)

### Features
* `uniqsketch`: added `--min-margin=N` to harden signature selection against single-base sequencing errors. With `--min-margin=2`, uniqsketch prefers signatures that lie at Hamming distance ≥ 2 from every k-mer in other references, so a single substitution error in a read cannot turn a foreign k-mer into one of a reference's signatures — a source of false-positive hits. It is a tiered preference: within each genomic selection slot a 2-safe, non-low-complexity candidate is chosen when available, falling back to the previous behavior only when a slot has no 2-safe option, so per-reference signature counts and genomic spacing are preserved. A summary line reports how many selected signatures met the margin. The default (`--min-margin=1`) leaves selection unchanged. Currently supports margins 1 and 2; higher margins are planned.

## 1.4.0 (2026-07-16)

### Features
* `comparesketch`: added `--low-mem`, a streaming M×N comparison mode for large reference sets. The default mode pre-caches every reference's k-mer hashes (M+N file reads) but its memory scales with the entire reference universe — for a few thousand multi-megabase genomes this can exceed 1 TB. With `--low-mem`, only one Bloom filter and one reference's k-mers are held per thread at a time: each first-set reference is loaded into a filter and every second-set reference is re-read from disk and queried against it. Memory is O(threads × genome) instead of O(all genomes), at the cost of M×N (rather than M+N) file reads. The similarity output is identical to the default mode; only the memory/I/O profile changes.
